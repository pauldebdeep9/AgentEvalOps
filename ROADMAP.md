- **Open gap, found 2026-08-03: the platform does not distinguish infrastructure failure from agent/evaluation failure — an infra failure during any task currently discards the entire run's results rather than scoring or reporting anything.** Investigated by tracing the actual code path (not just reading it) against the real partial bundle from the 2026-08-03 `OpenAIRunner` live-verification attempt, preserved at `tests/fixtures/bundles/partial-infra-failure-2026-08-03/` (see its README for full provenance). Findings, evidence-first:
  - `core/schemas.py:72` defines `TerminationReason.INFRA_FAILURE`, and it is exercised by exactly one place in the whole codebase: `tests/test_core_schemas.py:94`, an isolated unit test asserting its string value. `grep -rn "INFRA_FAILURE" src/` finds no other hits — no runner, orchestrator, evaluator, or report code ever constructs an `AgentOutput` or trace event carrying it. The vocabulary exists; the behavior doesn't.
  - `core/errors.py`'s `InfrastructureError` docstring states the intended contract plainly: *"Agent-level failures (wrong answer, agent giving up) are NOT this exception — those are captured in `AgentOutput.termination_reason`."* Both runners honor the raise side of that contract correctly (`agents/openai_runner.py:365-366`, `agents/langgraph_runner.py:338-339`: a blanket `except Exception as exc: raise InfrastructureError(...)` around the model API call — this is not 429-specific, it uniformly wraps timeouts, 5xx, network errors, and auth failures alike). But nothing implements the *catch* side of that contract.
  - `orchestration/local.py`'s `LocalOrchestrator.run()` (lines 135-149) only catches `(KeyboardInterrupt, asyncio.CancelledError)` around `asyncio.gather(*futures)`. `InfrastructureError` is neither, so it propagates straight out of `run()` — skipping the per-task result loop, `trace_store.finalize()`, `SimpleScorer().score(...)`, and `policy_checker.check(...)` for **every** task in the run, not just the one that failed. `cli.py`'s `run` command (lines 130-132) only catches it around the top-level `asyncio.run(orchestrator.run())` call — prints `"Infrastructure error: {exc}"` to stderr and exits 1, before `_print_summary()` or `BundleWriter.write()` are ever reached.
  - **Correction to how this was initially framed going into the investigation:** the 2026-08-03 live run did **not** "report 0/2 passed, 0 tokens, $0.00" anywhere — that framing doesn't match the evidence. No `RunSummary` was ever returned, so `_print_summary()` never ran and no bundle beyond a stray `traces.jsonl` (two `agent.plan` events, no cost or terminal events — confirmed against the actual fixture) was ever written. The real defect is more severe than "an outage gets silently scored as failure": it's "an outage during any one task erases evaluation of the *entire* run, with no bundle, no report, and no summary of any kind" — confirmed via `validate-bundle` against the real bundle: `FAIL`, missing `metadata.json`, `config.json`, `evaluations.json`, `policy.json`, `summary.json`, `report.md`, and `manifest.json`.
  - `policy/basic_checker.py`'s `BasicPolicyChecker.check()` (lines 32-85) checks only cost ceiling, tool deny-list, and trace-event count — it never inspects `output.success`, `output.termination_reason`, or whether any tasks were evaluated at all. An all-infra-failed or empty run (`total_cost_usd=0.0`, `trace=[]`) trips none of its three checks, so it would return `Verdict.PASS`, `notes="all checks passed"` — a **false PASS on a run where nothing ran**, exactly the failure mode flagged as worse than an honest failure. (`orchestration/local.py`'s `_combined_output()` at line 40 does correctly compute `success=False` for an empty `task_results` list — but `BasicPolicyChecker` never consults that field, so the one correct signal that exists is never checked by the one component whose job is to catch this.) **CLOSED 2026-08-03** — `BasicPolicyChecker` no longer returns `PASS` on an unevaluated run; see the dedicated entry below. The other findings in this gap (orchestrator crash-through, report/scorer collapse, the malformed-response third path) are unaffected and remain open.
  - `reports/markdown.py`'s per-task table (lines 65-75) *would* render `infra_failure` correctly in its "Termination" column if an `AgentOutput` ever carried it — the per-row signal isn't designed away. But the report's headline aggregate (`- Tasks: {passed} / {total} passed ({failed} failed, {pass_rate:.0f}%)`, lines 50-53) and `RunSummary.passed_tasks`/`.failed_tasks` make no such distinction; `evaluators/deterministic.py`'s check 1 (`base_passed = output.success and output.termination_reason == COMPLETED`) folds `INFRA_FAILURE` into `passed=False`/`score=0.0` exactly like a genuine wrong answer or `AGENT_ERROR`. A reader trusting the headline number — the one DESIGN.md's regression-comparison use case actually consumes — cannot tell an outage from a bad answer.
  - A **third, quieter** behavior exists alongside the two above: a malformed/unexpected-*shape* API response (not an exception) never raises at all — both runners' `_ParsedResponse.__init__` reads every field via `getattr(obj, attr, default)`, so it silently produces zero-valued fields that typically resolve to `TerminationReason.AGENT_ERROR`, indistinguishable even in the evaluator's notes from a real agent mistake. So 429 is not special and the collapse is not one bug but three related ones: (a) transport/API exceptions → whole-run abort, nothing scored; (b) missing/bad API key (`ConfigurationError`) → same whole-run abort via a separate but equally uncaught path; (c) malformed response shape → silently absorbed as an ordinary agent failure.
  - **Verdict: this is a real defect, not primarily a documentation gap** — though a real documentation gap sits alongside it. The runner-level contract (raise vs. capture) *is* documented and correctly followed. What's undocumented is everything after the raise: `ARCHITECTURE.md` §5 only gestures at this ("if the orchestrator is interrupted (Ctrl-C, OOM, sandbox died) ... best effort to finalize the partial bundle") — language that groups "sandbox died" with `KeyboardInterrupt`, implying infra failures were meant to get the same best-effort-finalize treatment — but the code's actual except-clause never lists `InfrastructureError`. The code doesn't match its own architecture doc's stated intent, and there is no coherent *designed* behavior here to merely document — an accidental crash-through isn't a documented gap waiting for a docstring, it needs new code.
  - **Minimum honest fix (not implemented — recorded here per this task's explicit instruction not to touch scoring/schemas/the policy checker):** three coordinated layers, because a fix at only one layer reintroduces the collapse at the next:
    1. **Orchestrator**: `LocalOrchestrator._run_task` (or a wrapper) catches `InfrastructureError`/`ConfigurationError` per task and converts it into a `TaskRunResult` whose `AgentOutput.termination_reason = TerminationReason.INFRA_FAILURE`, `success=False`, `error=str(exc)` — finally using the enum value that already exists.
    2. **Schema (bundle-contract change — needs a decision, not a silent addition)**: `RunSummary.passed_tasks`/`.failed_tasks` are not enough — a third bucket (e.g. `infra_failed_tasks: int`) is needed so pass-rate semantics can be stated explicitly ("does the rate's denominator count attempted tasks, or only genuinely-evaluated ones?" — right now there's no field that would let a consumer even ask this). `EvaluationResult`'s binary `passed: bool` similarly can't represent "not evaluated" distinct from "evaluated and failed." Since `RunSummary`/`EvaluationResult` serialize into `summary.json`/`evaluations.json`, this is a bundle-format change under `ARCHITECTURE.md` §3's `schema_version` rule, not an internal refactor — exactly why it wasn't done in this session.

## 4. Critical path

These five items, if they slip, cascade into the v0.5 date slipping. Everything else has slack.

**Critical path item 1: Schemas + protocols (W2–W3).** Earliest start W2, latest finish W4. Slippage cost: every downstream week is built on these signatures. Mitigation: don't over-engineer in W2–W3 — get to compilable-and-type-clean fast, iterate the schemas in subsequent weeks while implementations are still thin. The bundle-version compatibility test means schema evolution is survivable.

**Critical path item 2: Real LangGraph + Claude runner (W8).** Earliest start W8, latest finish W16. Slippage cost: all AWS work (W17+) depends on a working real runner. **This is NOT required for v0.1 — v0.1 uses MockAgentRunner.** Mitigation: if LangGraph proves painful, fall back to a hand-rolled minimal agent loop (tool-call → execute → observe) using the Anthropic SDK directly. The architecture treats runners as pluggable; "LangGraph specifically" is not a requirement, "a real runner for v0.2" is.

**Critical path item 3: SWE-bench harness vendoring decision (W14).** Earliest start W14, latest finish W15. Slippage cost: this is the highest-uncertainty technical investigation in the whole plan. Mitigation: if upstream proves intractable (Docker-in-Docker on Fargate, harness API mismatches), descope to "SWE-bench Lite" instead of Verified, which has simpler grading. The result bundle is more impressive with Verified, but Lite still ships a real benchmark.

**Critical path item 4: Fargate eval runner end-to-end (W20).** Earliest start W19, latest finish W22. Slippage cost: this is the make-or-break for the AWS story. Mitigation: if Fargate proves stubborn, the fallback is "AWS Batch" or "EC2 with launch templates" — same `CloudBackend` interface, different implementation. The plan does not assume Fargate-specifically.

**Critical path item 5: SWE-bench on Fargate (W23–W24).** Earliest start W23, latest finish W25. Slippage cost: this is the v0.3 release and the centerpiece result bundle. Mitigation: if Docker-in-Docker on Fargate is blocked, switch to a "sandbox-as-Fargate-task" approach where each SWE-bench instance is its own Fargate task instead of a nested container. More expensive per run but unblocks the architecture.

The non-critical-path items — policy checker, scorers, report generators, COST_MODEL.md — have multi-week slack and can move around freely between W26 and W31.

Reserve 2 weeks of slack in the plan (the holiday buffer doubles as protocol-revision buffer if needed). | A new evaluator or runner in W20+ can't be expressed in the existing protocol shape |
| 8 | Scope creep — "while I'm here, let me also add MLE-bench / dashboard / AgentCore / FastAPI" | **H** | H | DESIGN.md non-goals are the answer; re-read them at the start of every month. If a feature isn't on this roadmap, it doesn't get built before v0.5. | Any week's commits include code in `benchmarks/mlebench/`, `dashboard/`, `api/`, or `cloud/aws/agentcore_jobs.py` |

Risk 8 is the highest-probability risk by a wide margin. The single most common way this plan fails is not a technical blocker but discipline failure — building the dashboard "because it's only a weekend" and then losing three weekends.

## 6. Scope-cut ladder

Re-baseline every 4 weeks. If behind schedule, execute the corresponding cut immediately, don't hope to catch up.

**If 2 weeks behind by Week 20 (Oct 4):** Cut the LLM-as-judge evaluator from v0.5 (defer to v0.7). Keep deterministic only. Removes ~1 week of effort. Minimum viable v0.5 still includes SWE-bench-on-AWS, which is the headline.

**If 4 weeks behind by Week 28 (Nov 29):** Cut the scorers (regression comparison) and the LLM-driven failure-analysis report. Replace with a simple cost-and-pass-rate markdown report. Remove the DynamoDB run index — bundles in S3 are enough. Removes ~2 weeks. Minimum viable v0.5 still includes SWE-bench-on-AWS with a real result bundle and policy checker.

**If 6 weeks behind by Week 32 (Dec 27):** Cut the AWS deployment entirely from v0.5 scope. Reposition v0.5 as "local-only platform with real SWE-bench Verified subset run locally," and pull AWS into v0.6 (target: March 2027). Removes ~6 weeks of AWS work. Minimum viable v0.5 still ships on Jan 4 with a real benchmark and real result bundle — just on a laptop, not on Fargate. **This is the load-bearing cut. AWS is the most visually impressive feature but is also the most slippable.** A v0.5 with no AWS is still a credible portfolio artifact; a v0.5 that misses Jan 4 to keep AWS in scope is not.

**If 8+ weeks behind:** Acknowledge the plan was wrong and re-baseline. Don't ship a v0.5 you're embarrassed by to hit a date.

## 7. Re-baselining cadence

The roadmap is checked against reality every 4 weeks, on the same day. Re-baseline checkpoints fall on:

- **W4 checkpoint (mid-Jun):** Are protocols + schemas + orchestrator on track? If W5 isn't running a mock task end-to-end, scope-cut now.
- **W8 checkpoint (mid-Jul):** Is the real LangGraph runner working? This is post-v0.1 work — it enables v0.2. If it's blocked, note the blocker and continue toward v0.1 (W11) using MockAgentRunner. Switch to a hand-rolled SDK loop if LangGraph proves intractable.
- **W12 checkpoint (mid-Aug):** Is replay working? Is v0.1 tagged? v0.1 was tagged 2026-07-05, well ahead of this checkpoint — that half is moot. "Is replay working" now means specifically W12c (W12a, the taxonomy/schema/provenance prerequisite, closed 2026-08-05; W12b, structural replay folded into `validate-bundle` plus `replay_command.txt`, closed 2026-08-04) — if W12c hasn't landed by mid-August, that's the signal for the 2-weeks-behind cut, not "replay" as an undifferentiated whole.
- **W16 checkpoint (mid-Sep):** Is SWE-bench grading working locally? Critical path checkpoint.
- **W20 checkpoint (early Oct):** Is `AwsBackend.submit_job` working? If not, execute the 4-weeks-behind cut.
- **W24 checkpoint (late Oct):** Is SWE-bench running on Fargate? Last chance to execute the "drop AWS from v0.5" cut while still maintaining a credible release.
- **W28 checkpoint (late Nov):** Is v0.4 feature-freeze achievable in 3 weeks? If not, lock scope now.

Each checkpoint is one hour of reflection, not a meeting. Write a one-paragraph note in `ROADMAP.md`'s changelog ("W12 checkpoint: replay working, v0.1 tagged on time, no cut needed"). That note is itself a portfolio artifact — it shows the discipline of a project that was planned, not just executed.

## 8. What this roadmap does not promise

This roadmap promises that *if the assumptions hold*, v0.5 ships in the week of January 4, 2027. The assumptions are: ~12 productive hours per week sustained, no major life disruption, AWS account access stays valid, Anthropic and Bedrock APIs remain available, SWE-bench Verified upstream remains usable.

It does not promise that the SWE-bench pass rate will be impressive. The portfolio value is in *the platform*, not in any one agent's score on any one benchmark. A v0.5 release that ships on time with a 12% pass rate is more credible than a delayed release with a 40% pass rate, because the platform is what's being demonstrated — the agent is just the most convenient thing to point it at.

It does not promise that the architecture won't need revisions in v0.6+. The schema versioning and the protocol-based extension model are designed for evolution. The roadmap is for *getting to a credible v0.5*, not for getting to the platonic final form.

If any of these assumptions changes, this document is updated and re-baselined. The roadmap is a tool, not a contract.
